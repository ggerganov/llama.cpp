# analog backend vs CPU backend - measured results

This file is generated by `benches/analog/compare.sh`. Measured on a 2 vCPU machine (gcc 12.2,
OpenMP, no BLAS), on a randomly initialized 4 layer / 256 embedding llama model quantized to Q8_0.
The model writes nonsense by construction, so its absolute perplexity is meaningless - only the
differences between the backends mean anything. Wall times on this machine vary by +-30% between
runs, the error columns are reproducible.

## Summary

| what | CPU backend | analog, ideal | analog, 4 bit cells |
| --- | ---: | ---: | ---: |
| model load | ~1.5 ms | ~1.5 ms | ~1.5 ms |
| first evaluation (programming the arrays) | 16.1 ms | 18.5 ms | 58.6 ms |
| prompt processing, 128 tokens | 14.1 ms | 12.4 ms | 12.6 ms |
| token generation | 0.45 ms | 0.33 ms | 0.37 ms |
| perplexity | 260.3720 | 260.3720 | 258.9893 |
| max logit error vs CPU | 0 | 0 | 0.121 |
| RMS logit error vs CPU | 0 | 0 | 0.034 |
| MUL_MAT error, RMS | 0 | 0 | 0.11 - 0.28 |
| modeled device cost of the run | - | 10.60 ms, 0.161 mJ | 10.60 ms, 0.161 mJ |

Observations:

- **Loading is not affected at all.** The weights are read into the same host buffers as before
  and the arrays are programmed lazily, the first time a matrix is used, so model loading is
  byte-for-byte the same work, and the ~1.5 ms of the row is the machine (the run in the raw output
  below was busier than the others). The *first evaluation* is the column that pays for
  programming.
- **The ideal array is bit-identical to the CPU backend**, at every level of the stack: the MUL_MAT
  maximum error is exactly 0, the perplexity matches to the last digit, and the logits (maximum
  error, RMS, KL divergence, argmax) match exactly. This is the check that the scheduling and the
  emulation plumbing are correct.
- **A 4 bit cell with a 2% programming error costs accuracy**: the RMS error of a single matrix
  multiplication is 11-28% of the output RMS and the logits move by 0.034 RMS (KL 0.0006 nats). On
  a random model the perplexity cannot show this (the output distribution is nearly uniform and the
  argmax is arbitrary), so the MUL_MAT table and the logits comparison are the meaningful accuracy
  measurements.
- **The emulation costs time**, and on this 2 vCPU machine most of it is the programming of the
  arrays (45.3 ms of the 58.6 ms of the first evaluation). Once the arrays exist, the passes add
  little to prompt processing (12.6 ms against 14.1 ms of the CPU backend, i.e. inside the noise)
  and to token generation (0.37 ms against 0.45 ms).
- **The passes are not the bottleneck of the emulation**, the emulated mixed-signal core is: the
  digital `MUL_MAT` runs 1508 times per evaluation and the passes touch the same data once. That is
  why the parallel kernels and the compute shaders of the next section buy time in the first
  evaluation and in the readout, and almost nothing in the steady state.
- **The three implementations of the passes agree bit for bit.** The kernel test checks the
  parallel CPU kernels and the mirror of the compute shaders against the scalar reference for every
  pass, shape and array configuration, and `test-analog-backend -d shader` checks the same for the
  whole model (9 `MUL_MAT` cases, error exactly 0). Both run at the beginning of this script.

## Speed of the digital kernel against the analog array

The table below separates the three things that are easy to confuse: what the digital CPU kernel
does, what the *emulation* of the analog device does on the same CPU, and what the *modeled*
analog device would do. The modeled columns come from the device model (128x128 tiles, 300 ns per
array pass, 0.1 pJ per MAC by default).

### One MUL_MAT at a time

| case | digital CPU | analog, emulated | analog, modeled | modeled vs digital |
| --- | ---: | ---: | ---: | ---: |
| f32 256x256, 1 column | 5 us | 7 us | 0.60 us | 8.3x faster |
| f32 512x512, 4 columns | 31 us | 29 us | 4.80 us | 6.5x faster |
| f16 512x1024, 1 column | 28 us | 30 us | 1.20 us | 23x faster |
| q8_0 512x512, 1 column | 10 us | 12 us | 1.20 us | 8.3x faster |
| q8_0 1024x512, 8 columns | 56 us | 67 us | 19.2 us | 2.9x faster |
| q4_0 512x512, 1 column | 12 us | 14 us | 1.20 us | 10x faster |
| q4_0 1024x1024, 4 columns | 65 us | 75 us | 9.60 us | 6.8x faster |
| q4_k 1024x512, 1 column | 16 us | 18 us | 2.40 us | 6.7x faster |
| iq2 1024x512, 1 column | 30 us | 27 us | 2.40 us | 12.5x faster |

The modeled array time is `ncols * ceil(K/128) * 300 ns`, i.e. it is set by how many times the
input has to be swept through the array, not by the arithmetic. That is why the gap is largest for
single column (token generation) shapes, where the digital kernel is limited by memory bandwidth,
and smallest for wide batches, where the digital kernel has more arithmetic to amortize the loads
over.

### Whole model

| | digital CPU | analog, emulated | analog, modeled |
| --- | ---: | ---: | ---: |
| prompt of 128 tokens | 14.1 ms | 12.6 ms | 2.38 ms |
| one generated token | 0.45 ms | 0.37 ms | 0.0222 ms |
| energy | - | - | 0.347 uJ/token |
| effective throughput, one MAC per cell per token | 8.4 G MAC/s (pp), 2.0 G MAC/s (tg) | same as the CPU plus the passes | 49 G MAC/s (pp), 41 G MAC/s (tg) |

The modeled numbers only depend on the assumed pass latency. Sweeping it with
`GGML_ANALOG_MVM_LATENCY_NS`:

| assumed pass latency | pp, modeled | tg, modeled | pp vs digital CPU | tg vs digital CPU |
| --- | ---: | ---: | ---: | ---: |
| 100 ns | 0.795 ms | 0.0074 ms | 17.7x faster | 61x faster |
| 300 ns (default) | 2.384 ms | 0.0222 ms | 5.9x faster | 20x faster |
| 1000 ns | 7.948 ms | 0.0740 ms | 1.8x faster | 6.1x faster |
| 3000 ns | 23.844 ms | 0.2220 ms | 1.7x slower | 2.0x faster |

So on this model the modeled array overtakes the digital CPU kernel up to ~1.7 us per array pass
for prompt processing and up to ~4.9 us per pass for token generation; beyond that the digital
kernel wins. Energy is independent of the latency in the model: 0.347 uJ per generated token.
